# 论文深度分析 Skill

对指定论文（arXiv ID、论文标题、URL 或本地 PDF）进行研究级深度分析，生成一份可支持选题、复现和方法判断的笔记。默认读者是博士生、博士后或高校研究人员；可以解释基础概念，但不得因此降低证据标准。**先准确保存作者写的摘要及其中文译文，再另写自己的理解和批判性分析**；不要把摘要翻译写成个人解读，也不要把精读写成摘要扩写。输出是标准 Markdown，不使用笔记软件专有语法。

开始分析前先读取同级共享准则 `../research-evaluation-rubric.md`。其中的“检索预筛与全文评价边界”“分类型审查”“证据锚点”和“标准研究输出”是本 skill 的评价口径。

---

## 语言设置

通过 `--language zh` 或 `--language en` 指定输出语言，默认中文（`zh`）。如果没有显式指定，可根据用户当前对话使用的语言自动判断。语言设置贯穿全文（章节标题、正文内容需保持一致）。

---

## 输出位置

默认输出到**工作区内的笔记根目录** `<notes_dir>/<YYYY-MM>/<论文主干>/精读.md`：`notes_dir` 取自工作区配置（默认 `03-notes`），`YYYY-MM` 是该论文的入库月份，`<论文主干>` 与 `01-raw/YYYY-MM/<论文主干>.pdf` 完全一致。图片放在同一论文目录的 `images/` 下：

```text
03-notes/
└── YYYY-MM/
    └── <论文主干>/
        ├── 精读.md
        └── images/fig1.png ...
```

- **月份口径**：`YYYY-MM` = 论文**首次进入 `01-raw` 的日期所在月**，与 `.AGENT.md` 一致；同一篇论文在 `01-raw`、`02-markdown`、`03-notes`、`06-translation` 四处的月份与主干必须相同。
- `generate_note.py` 会**自动从 `01-raw/YYYY-MM/` 中同名 PDF 所在月份目录推断**该月份，找不到时用当前月份兜底；也可以用 `--month` 显式指定。
- `--domain` 只写入笔记 frontmatter（用于检索/分类标注），**不再用于目录分组**。
- `--output-dir` 仍保留，用于覆盖**笔记根目录**（即 `notes_dir`）；默认从工作区配置读取（`03-notes`）。已不再有 `PAPER_NOTES_DIR` 环境变量或 `./paper-notes` 默认值。

笔记与其 `images/` 文件夹应保持相对路径关系，这样整个 `<论文主干>/` 连同 `精读.md` 一起复制/分享到任何地方，图片依然能正常显示。

## 工作流程

### Step 0：初始化

```bash
mkdir -p /tmp/paper_analysis
cd /tmp/paper_analysis     # 仅用于下载 PDF 与提取图片的临时目录

# 笔记落盘位置由 generate_note.py 自行解析（向上识别工作区 → 读 notes_dir），
# 因此不需要在这里拼路径；若当前目录不在工作区内，显式传 --workspace <工作区根> 即可。
# 目标：<工作区>/<notes_dir>/<YYYY-MM>/<论文主干>/{精读.md, images/}
```

### Step 1：识别论文

接受以下输入格式：
- arXiv ID：`2402.12345` 或 `arXiv:2402.12345`
- 论文标题（用于搜索）
- 论文 URL（arXiv / OpenReview / Hugging Face Papers 等）
- 本地 PDF 文件路径（用户已上传）

**检查是否已分析过**：在笔记根目录 `$NOTES_DIR` 的 `YYYY-MM/` 月份目录下按 arXiv ID 或标题搜索已有 `精读.md`，若找到则直接读取返回，避免重复分析（除非用户要求重新分析）。

### Step 2：获取论文内容

记录实际使用的论文版本、来源和访问日期。优先以论文 PDF 中的摘要和正文为准；若 arXiv API、期刊页面与 PDF 的摘要或版本不同，标明差异，不拼接多个版本。正文、附录和补充材料是全文评价的主要依据；只取得摘要时按共享准则停留在初评，不伪装成精读。

**2.1 元数据**

优先使用 arXiv API 获取结构化元数据：

```
GET http://export.arxiv.org/api/query?id_list=[PAPER_ID]
```

提取：标题、作者、摘要、发布日期、分类（categories）、链接。

**2.2 PDF 正文**

- 如果用户已上传 PDF，直接使用（参考 `pdf-reading` skill 提取文本/结构）。
- 否则下载：

```bash
curl -L "https://arxiv.org/pdf/[PAPER_ID]" -o /tmp/paper_analysis/[PAPER_ID].pdf
```

**2.3 提取图片（用于图文并茂）**

使用 `pdf` / `pdf-reading` skill 从 PDF 中提取插图（架构图、方法图、实验结果图等），保存为标准图片格式：

```bash
# 示例：将图片保存到笔记对应的 images 目录（月份须与 01-raw 中该论文的月份一致）
NOTE_IMAGES_DIR="$NOTES_DIR/YYYY-MM/[paper-title]/images"
mkdir -p "$NOTE_IMAGES_DIR"
# 提取出的图片统一重命名为 fig1.png, fig2.png, ... 并保存到此目录
```

命名规则：`fig1.png`、`fig2.png`……按论文中出现顺序编号，便于在正文中引用。

**2.4（可选）源码包**

如果需要更精确的正文内容（而不仅是 PDF 提取文本），可选下载 e-print 源码：

```bash
curl -L "https://arxiv.org/e-print/[PAPER_ID]" -o /tmp/paper_analysis/[PAPER_ID].tar.gz
tar -xzf /tmp/paper_analysis/[PAPER_ID].tar.gz -C /tmp/paper_analysis/
```

这一步是加分项，不是必须的——PDF 提取的文本通常已经足够支撑深度分析。

### Step 3：深度分析

先判断论文类型（理论 / 实证方法 / 系统 / 数据集与基准 / 综述与观点 / 混合型），再按 `../research-evaluation-rubric.md` 做分类型审查。**摘要与正文采用不同写法**：摘要保真；正文是有来源锚点的独立讲解、核算和评价。

#### 3.1 摘要保真：原文、译文、理解分栏

- **英文原文摘要**：从所分析版本的 PDF 摘要区完整转录，保留原句顺序、术语、数字和限定词；不删节、改写、重组或混入自己的判断。OCR 无法辨认的词应回看原页；仍不确定则标记并说明。若论文原始摘要不是英文，标题改为“原文摘要”并注明语言，不自行编造英文版。
- **中文对应翻译**（`zh`）：按原文句序和语义逐句忠实翻译，保留数量、方向、条件、比较对象与不确定语气。专有名词首次出现可写“中文（English）”；不能把 `may` 译成“证明”，不能把作者声称的结果写成已独立核验的事实。若 `en` 输出，保留原文摘要，按用户要求决定是否另附翻译。
- **核心要点／我的理解**：放在上述两栏之后并明确标为分析者概括。分别说明问题、方法、结果、贡献和最重要的待核验点；这部分可以重述与评价，但不得替代前两栏。
- 不从 API 摘要推测 PDF 原文。若 PDF 摘要无法取得，写明“原文摘要未核对”，展示能核实的来源版本；译文对应同一版本，不能标为 PDF 原文。

#### 3.2 正文的展开深度

完整精读要让读者**不打开论文也能理解核心技术路径和证据边界**，同时能凭章节、式号、定理、表号、图号或附录定位原文。常规方法/实验论文的中文分析正文通常应达到约 5000–9000 汉字；理论、系统和长论文可按复杂度增加。这个范围用于防止过度压缩，不为凑篇幅重复内容；资料不足时缩短并说明缺口。表格、列表和图不能代替解释性段落。下列适用部分逐项展开，非适用内容说明原因：

1. **研究背景、问题和动机**：解释任务定义、输入输出、约束、现有技术路线及其具体瓶颈；把“作者认为的空白”与经近邻对照核实的空白分开。写清论文要回答的研究问题和成功判据。
2. **方法或理论主线**：先用一段直观解释，再按数据流或证明链逐步讲。给出必要的符号定义、关键公式、各模块输入输出、训练/推理或算法步骤、复杂度与关键假设；解释每个设计为何需要、与已有做法有何差异。对核心公式说明其作用、推导前提及与前后公式的联系，不只抄公式或罗列模块名。理论论文应详述主定理、假设、关键证明步骤、界的改进以及实现代价。
3. **实验或其他验证**：交代数据集/任务、划分、指标方向、强基线、公平性设置、预算和复现条件。提取核心结果的原始数值及单位，按同一指标计算绝对/相对差异并注明算式口径；解释哪些结果真正支撑主张，哪些仅是相关现象。逐项分析消融、敏感性、统计波动、失败案例和未覆盖边界。无实验的理论/综述论文改用适合其贡献的证明、反例、覆盖性或论证审查，不补造实验表。
4. **主张—证据—限制**：把论文的 2–5 个核心主张拆开，每项标明正文证据位置、证据所能支持的最强结论、竞争解释、适用条件及置信度；对未证实的推断明确写“推测/待核验”。正文中展开最关键的争议点，矩阵只作索引。
5. **最接近工作与技术定位**：查阅能直接挑战新颖性的 2–5 篇原始论文，给出可核验链接或标识。比较共同问题、假设、方法、评测协议与结果，指出净增量是否能归因于本文设计；不能仅复述本文 Related Work 或按发表时间罗列。若只有少量真正近邻，如实说明。
6. **深度评价与复现**：分别写理论贡献、实际用途、优势、致命问题（若有证据）与非致命局限、适用/不适用场景。检查关键假设、数据泄漏、基线公平性、统计不确定性、代码/数据/超参/算力/证明细节；列出一个最小复现或反证方案，说明资源、指标、成功及停止条件。
7. **后续研究机会与阅读决策**：提出 1–3 个可证伪假设，每项说明来自哪一处证据缺口、最小验证、预期结果和失败判据。按共享八维量表评分，逐维附证据与理由；分开报告学术价值、当前课题契合度和阅读优先级。若用户的具体课题未知，不臆测契合度，标为待定并说明需要什么信息。

写作时优先形成“问题 → 技术选择 → 证据 → 解释 → 边界”的连续论证。每个重要数字、方法判断和对比结论尽量紧邻原文锚点；严禁用“显著提升”“实验充分”“很有潜力”代替具体数值、比较条件和原因。

### Step 4：公式与图片渲染规范（关键）

这是本 skill 相比通用写作最重要的约束，确保笔记在任何标准 Markdown 环境中都能正确渲染。
**本节全部规则对"直接输出给用户的聊天回复"（如 Step 6 的分析摘要、任何含公式的解释文字）
同等强制**——用户在渲染后的界面里阅读回复，公式写法不合规同样会显示成乱码；
发送前与写笔记一样先自查一遍：

**公式**
- 行内公式：`$...$`，例如：模型目标是最小化 $L(\theta)$。**禁止使用 `\( ... \)` 定界符**，
  禁止用反引号把公式包成代码，也不要裸写 Unicode 数学符号（如 ‖∇f(x)‖、η_t）充当公式。
- 行内公式细则（Typora 等渲染器的硬性要求，违反任何一条都会渲染失败）：
  - `$` 与公式内容之间**不留空格**（写 `$x_t$`，不要写 `$ x_t $`）；
  - 行内公式与前后的中文字符/中文标点之间**各留一个半角空格**（"其中 $\eta_t$ 是学习率" ✅ / "其中$\eta_t$是学习率" ❌）；
  - `$...$` 必须在同一行内闭合，不要跨行书写；
  - 表格单元格内的公式禁止出现裸 `|` 字符（会被当成列分隔符），条件符号用 `\mid`，范数一律写 `\Vert x \Vert`。
- 块级公式：`$$...$$`，且**独立成行，前后各空一行**（提升在 GitHub / VS Code / Typora 等不同解析器下的兼容性）：

  ```
  损失函数定义为：

  $$
  \theta^* = \arg\min_\theta L(\theta)
  $$

  其中 ...
  ```
- 公式编号不用 `\tag{}`，改在正文文字里标注（如 "即论文中的式 (4)："）。
- 命令只用基础子集：`\frac`、`\sqrt`、`\nabla`、`\mathbb`、`\mathcal`、上下标（多字符下标必须加花括号，如 `x_{t+1}`）、
  希腊字母、`\le`/`\ge`、`\min`/`\max`、`\sum`、`\arg`、`\propto`、`\Rightarrow`、`\left( \right)`、`\Vert`、`\mid`、`\cdot`、`\top`。
- **禁止**使用以下易导致整段渲染成乱码的命令：`\tag{n}`、`\big`/`\Big`/`\bigl` 系列、`\lesssim`、
  `\;` `\,` `\!` `\quad` 等间距命令、`\boxed`、`\underbrace`/`\overbrace`、`\overset`/`\underset`、
  `\|`（必须换成 `\Vert`）、`\text{}` 里嵌中文（公式内需要文字说明时，把文字挪到公式外的正文里）。
- **禁止**用三个反引号代码块包裹需要渲染的公式（那样只会显示成代码而不是公式）。
- **禁止**用纯文本伪公式（如 `theta* = argmin_theta L(theta)`）代替 LaTeX。
- 符号**含义**尽量与原论文保持一致，但**书写命令**必须按上述白名单转换（例如原文的 `\|` 改写成 `\Vert`、去掉 `\tag{}`）。
- 写入笔记前逐条自查：行内定界符是否为 `$...$`、`$` 内侧是否贴了空格、与中文之间是否留了空格、
  `$...$` 是否同行闭合、是否混入禁用命令、表格单元格内是否有裸 `|`。

**图片**
- 一律使用标准 Markdown 图片语法：`![图注](images/fig1.png)`。
- 路径使用**相对路径**（相对于笔记 `.md` 文件），不要用绝对路径或特定笔记软件的图片语法。
- 每张图配一句简短说明其含义：

  ```markdown
  ![图1：整体架构，输入经过编码器后...](images/fig1.png)

  > 图1：[对图中各部分含义及关系的说明]
  ```

**架构图（当论文没有合适的现成图时）**
- 优先使用论文原图。
- 论文确实没有可用架构图时，用 **Mermaid** 代码块画流程图/架构图——GitHub、VS Code、Typora、大多数 Markdown 预览工具都原生支持渲染：

  ```mermaid
  flowchart LR
      A[输入] --> B[模块1]
      B --> C[模块2]
      C --> D[输出]
  ```
- 不再使用 ASCII 手绘图或任何笔记软件的 Canvas 功能作为架构图的备选方案。

**内部引用/相关论文**
- 不使用双中括号链接语法。
- 如果相关论文也生成了本地笔记，用标准 Markdown 相对链接，指向对方论文目录下的 `精读.md`：
  例如同月论文用 `[论文标题](../其他论文主干/精读.md)`，跨月论文用 `[论文标题](../../2026-07/其他论文主干/精读.md)`（相对当前 `精读.md` 所在位置换算）。
- 如果没有对应的本地笔记，直接用加粗文字标出标题即可：`**相关论文标题**（作者, 年份）`。

**提示/警告**
- 不使用 `> [!tip]` 这类笔记软件专有的 callout 语法（很多 Markdown 渲染器不支持，会原样显示成文字）。
- 用标准引用块 + 加粗代替：

  ```markdown
  > **关键启示：** 论文最重要的启示，一句话总结核心思想。

  > **注意事项：**
  > - 事项1
  > - 事项2
  ```

**Frontmatter（可选）**
- 如果需要程序化处理（检索、去重），可以保留一段简单的 YAML frontmatter，但这只是普通元数据，不依赖任何特定软件解析规则。字符串统一加双引号即可，没有额外的转义要求。

### Step 5：生成笔记

```bash
python3 scripts/generate_note.py \
  --paper-id "[PAPER_ID]" \
  --title "[标题]" \
  --authors "[作者]" \
  --domain "LLM" \
  --language zh
# 可选：--workspace、--notes-dir、--month、--output-dir（覆盖根目录）、--force
```

默认写入 `<notes_dir>/<YYYY-MM>/<论文主干>/精读.md` 并同时建好同目录的 `images/`；**已存在的 `精读.md` 默认不覆盖**（会提示"已存在精读笔记，未覆盖"），确实需要重写时加 `--force`。

脚本只生成带占位符的 Markdown 骨架，不代表分析已完成。逐节用核实过的内容替换占位符；尤其要把**PDF 的英文原版摘要完整填入“英文摘要”**，把与之对应的忠实译文填入“中文翻译”，再在“核心要点提炼”单独写自己的理解。按 Step 3.2 扩写骨架中较短的提示语，补足详细方法、结果解释、近邻对照、复现审计和研究判断；删除最终笔记中未填的占位符、虚构图片链接和不适用的空小节。

**月份推断规则（用于确定 `<YYYY-MM>` 目录，本身无特殊含义）**：
- 月份 = 该论文**首次进入 `01-raw` 的日期所在月**，即 `01-raw/YYYY-MM/` 中同名 PDF 所在的月份目录。
- 脚本在 `01-raw/` 下按 `YYYY-MM/` 逐月查找与该论文主干匹配的 PDF，取所在月份；**找不到同名 PDF 时用当前月份**。
- 也可以用 `--month "2026-09"` 显式指定，覆盖自动推断。
- `--domain` 只写入 frontmatter，**不再用于目录分组**。取值仍可按内容粗略判断（仅影响 frontmatter 标注）：
  - 提到 agent / swarm / multi-agent / orchestration → `Agent`
  - 提到 vision / visual / image / video → `Multimodal`
  - 提到 reinforcement learning / RL → `RL`
  - 提到 language model / LLM / MoE → `LLM`
  - 否则 → `Other`

### Step 6：输出分析摘要

分析完成后，向用户展示简要摘要（评分、亮点、优劣势、相关论文、笔记文件路径），并提示笔记文件已生成在 `<notes_dir>/<YYYY-MM>/<论文主干>/精读.md`（脚本运行时会把工作区、入库月份、笔记路径与图片目录打印出来），可以直接用任意 Markdown 工具打开。

## 评价标准

严格使用 `../research-evaluation-rubric.md`，不要再使用“创新性 / 技术质量 / 实验充分性 / 写作质量 / 实用性”五项简单平均：

- 先标论文类型，再决定适用证据；理论工作不得因“偏理论”扣分。
- 八个维度按 1-5 分或 N/A 评价，分数必须附证据位置、理由和置信度。
- 学术价值分与当前课题优先级分开报告；高学术价值不自动等于当前必读。
- 只读到摘要时不得输出全文质量分，只能给低置信度初评并标“待全文核验”。
- 写作清晰度作为可读性说明，不混入学术价值分，除非表述问题导致主张不可核验。

## 重要规则

- **摘要三栏不可合并**：英文原文为论文作者文本，中文为其对应译文，核心要点才是分析者的理解；原文和译文不得用摘要扩写或点评代替。
- **充分展开正文**：不要把大纲中的一行占位提示直接替换成一行概括。方法、关键公式、实验结果、最强近邻和局限都要有解释性段落与具体证据；表格是索引，不是正文替代品。
- **交付前核对**：确认原文摘要与所分析版本一致、译文没有增加结论、重要数值和比较口径可追溯、每个主要判断有证据锚点、占位符已清除、图片路径可打开，并区分作者主张和自己的推断。
- **只输出标准 Markdown**：不使用任何笔记软件专有语法，确保笔记可以独立打开、分享、渲染。
- **图片必须能独立渲染**：使用相对路径的标准 `![]()` 语法，笔记文件与 `images/` 文件夹一起移动/分享时图片依然可见。
- **公式必须能独立渲染**：统一使用 `$...$` / `$$...$$`，不要用代码块包裹、不要用伪公式代替；
  行内公式 `$` 内侧不留空格、与中文之间各留一个半角空格，命令严格遵守 Step 4 的白名单/黑名单。
- **保留用户已有笔记**：如果目标路径已有手动编辑过的笔记，不要覆盖，除非用户明确要求重新分析。
- **图文并茂**：论文中的核心图（架构图、方法图、关键实验图）都应提取并插入到笔记对应位置。
- **根据 `--language` 选择输出语言**：章节标题和正文都要保持语言一致。
- **优雅处理错误**：某一个信息来源失败（如源码包下载失败）不应中断整个分析，在笔记中如实注明该处信息不可得即可。

## 错误处理

- **论文未找到**：检查 ID/标题格式是否正确，提示用户换个关键词搜索。
- **arXiv 无法访问**：如实在笔记中注明该来源不可用，尽量用已有信息（如用户上传的 PDF）继续分析。
- **PDF 图片提取失败**：退化为仅描述图片内容（文字说明），并在笔记中注明"原图提取失败"。
- **相关论文检索不到**：如实说明缺乏对比语境，不要编造论文。
