# paper-weekly —— 周期研究现状与优化方向分析

从首次调用日起算，**每隔 `interval_days`（默认 7 天）**做一次研究组级别的分析：先建立本周问题地图与证据版图，再判断论文之间的增量、共识、冲突和空白，之后结合用户的公式卡点与当前课题约束，给出可证伪的研究机会和下一步行动。

开始分析前读取 `../research-evaluation-rubric.md`。默认读者是博士生、博士后或高校研究人员；周报的目的不是汇总“读了什么”，而是回答“领域证据发生了什么变化、哪些结论可信、当前课题应据此改变什么”。

本 skill 只读素材、只写报告，不生成论文笔记、不解析 PDF、不改任何素材。

## 研究主题的唯一真相源

**研究目标和主题一律从 `config.yaml` 的 `research_domains` 读取，本 skill 不内置、不硬编码任何具体主题。**

- 报告里的主题骨架 = `manifest.domains`（配置里的领域名，按顺序）
- 主题关键词 = `manifest.domain_keywords`（每个域的前若干个关键词）
- 需要改主题时**不要去改本 SKILL.md**，用 `paper-interests` skill 或直接改 `config.yaml`
- 配置里没有 `research_domains` 时：**先提示用户去配置**，不要自己编主题；此时报告无法按主题组织，应明确说明原因

本文件与示例中出现的领域名（如"随机梯度与优化理论"）**只是格式示例**，实际以配置为准。

# 周期与配置

配置在共享的 `.claude/skills/config.yaml` 的 `weekly` 段：

```yaml
weekly:
  enabled: true
  interval_days: 7      # 距上次分析满 7 天才再次运行（从首次调用日起算）
  window_days: 7        # 每次分析读取最近 N 天的素材
  start_date: ""        # 首次调用时脚本自动写入
  last_run: ""          # 每次成功后脚本自动写入
  history_size: 40      # 送入分析的论文数量上限
  note_pattern: "{week_start}-第{week_no}周周报.md"   # 周报文件名
  theme_first: true     # 分析范围以研究主题为主、论文范围为辅
  use_git_history: true # 用 git 提交记录判定"本周新增了哪些论文"
  git_lookback_days: 30
  inputs:               # 素材目录，按优先级排列（前面的优先读）
    - "03-notes"        # 你的精读判断，信息密度最高
    - "02-markdown"     # 解析全文，按需查证
  context_dirs:         # 附加上下文：只标注资产是否存在，不读正文
    - "06-translation"
    - "04-equation_problem"
```

`start_date` / `last_run` **由脚本维护，不要手改**。判断逻辑：`last_run`（没有则用 `start_date`）+ `interval_days` ≤ 今天 才到期。

**周序号**：`start_date` 所在周为**第 1 周**，每满 `interval_days` 进一位。报告名由 `note_pattern` 生成（如 `2026-09-21-第2周周报.md`）。

# 工作流程

## 步骤1：检查是否到期并收集素材

```bash
python scripts/collect.py --output weekly_manifest.json
```

只做一件事：判断周期 + 汇总素材清单。三种结果：

| 输出 | 含义 | 你该做什么 |
|---|---|---|
| `due: false` | 未到期 | **停止**，告诉用户下次日期即可，不要强行分析 |
| 到期 + 素材为空 | 到期但这周没有新论文 | 告知用户"本周没有新增素材"，仍可 `--mark-run` 推进周期，或询问是否要扩大窗口 |
| 到期 + 有素材 | 正常 | 进入步骤2 |

`--force` 可忽略间隔强制分析（用户主动要求"现在就来一次"时用）。

**清单 JSON 结构**（这是你要读的东西，不要自己去 rglob workspace）：

```json
{
  "schedule": {"due": true, "start_date": "...", "last_run": "...", "next_due": "..."},
  "week": {"week_no": 2, "week_start": "2026-09-21", "week_end": "2026-09-27",
           "suggested_filename": "2026-09-21-第2周周报.md"},
  "report_path": "<workspace>/07-research/2026-09-21-第2周周报.md",
  "theme_first": true,
  "window": {"since": "2026-09-15", "until": "2026-09-21"},
  "domains": ["随机梯度与优化理论", "大模型训练优化"],
  "domain_keywords": {"随机梯度与优化理论": ["stochastic gradient descent", "..."]},
  "git_added": {
    "available": true, "commits": 8, "stems": ["..."],
    "files": [{"stem": "...", "first_commit_date": "2026-09-15",
               "commit_subject": "docs(paper): 新增 PowerStep 精读资料", "files": ["..."]}]
  },
  "daily_dirs": [{"date": "2026-09-16", "search_result": "...", "titles": ["..."]}],
  "papers": [
    {"stem": "...", "month": "2026-09", "mtime": "...", "priority": 1,
     "roots": ["03-notes", "02-markdown"],
     "git_added": "2026-09-15", "git_subject": "docs(paper): ...",
     "assets": {"04-equation_problem": ["全局推理.md"], "06-translation": ["双栏对比.pdf"]},
     "files": [{"path": "03-notes/2026-09/<标题>/精读.md", "kind": "md", "root": "03-notes"},
               {"path": "02-markdown/2026-09/<标题>.md", "kind": "md", "root": "02-markdown"}]}
  ],
  "papers_total": 12
}
```

**月份目录会被递归识别**：

- `01-raw`、`02-markdown`、`03-notes`、`06-translation` 按 `YYYY-MM/` 分层（月份 = 论文首次进入 `01-raw` 的日期所在月），同一篇论文在这四个阶段**月份与主干一致**。
- `collect.py` 已支持跳过 `YYYY-MM` 段识别论文主干：`02-markdown/2026-09/<标题>.md` 取文件名主干，`03-notes/2026-09/<标题>/精读.md` 取论文目录名主干，因此两者能归并成同一篇；`03-notes` 的 `files[].path` 因此是 `03-notes/<YYYY-MM>/<标题>/精读.md` 这样的月份路径。
- `06-translation` 的资产扫描会**先遍历月份、再遍历论文目录**（`YYYY-MM/<论文标题>/`），所以翻译资产同样按月份归属。
- 每周新增论文的月份可直接从 manifest 的 `papers[].month` 字段读取；周报里引用论文时请统一使用 `01-raw/<month>/…`、`02-markdown/<month>/…`、`03-notes/<month>/…`、`06-translation/<month>/…` 形式，不要写成平铺的 `01-raw/<标题>.pdf`。
- `04-equation_problem/<论文标题>/` 与 `08-reading/<论文标题>/` **不按月份分层**，清单里的 `assets` 键仍是目录名。

**`git_added` 就是"本周具体提交了哪些论文"的权威答案**：按 `git log --diff-filter=A` 取新增文件，所以批量解析、clone、同步都不会污染结果；每篇带 `first_commit_date` 与提交信息，可以直接写"本周提交了 X"。

## 步骤2：两阶段读取（先宏观、再针对性）

**第一阶段——宏观：先搞清这一周研究主题的发展**

1. 读 `daily_topics`：这是 `08-daily` 逐日检索结果聚合出的全景（题目、领域分布、高分题），**成本最低**，先靠它建立"这一周领域里出现了什么"的整体印象。
2. 读 `03-notes`（`inputs` 里优先级最高的正文素材）：你自己的精读判断，信息密度最高。
3. `02-markdown` 是解析全文（单篇 40–150 KB），**只在查证具体公式/实验数字时定点读**，不要逐篇通读。
4. `git_added` 是"本周具体提交了哪些论文"的权威答案（含提交日期与提交信息）；与 `mtime` 冲突时以 git 为准。

**第二阶段——针对性：找出你不理解的地方**

5. 读 `reading_log`：来自 `08-reading` 的问答记录，是判断**卡点与掌握程度**的最佳信号。
6. 读每篇 `papers[].assets["04-equation_problem"]`：其中
   - `question_files` 是你自己写的疑问（文件名含"疑问/问题/不懂"等），**已带开头片段**，直接用它做针对性分析
   - `headings` 是推导稿的标题骨架，用来看这篇推到了哪一步，**不要读正文**（24–48 KB）
7. `assets["06-translation"]` 只用于判断你在这篇上花过多少功夫（`extract=existence_only`）。

**然后**才动笔：先做跨论文综合与主张-证据对照，再分析用户卡点，最后形成有新颖性基线、验证方案和停止条件的研究机会组合。

### 研究人员分析纪律

1. 先标注每篇论文类型，再按共享准则选择理论、实证、系统或数据集证据标准。
2. 区分作者主张、论文证据、你的推断和尚未证实，不把摘要措辞当结论。
3. “新增论文数量”不等于领域进展；单周主题数量也不能直接叫趋势，除非与可比历史窗口对照。
4. 引用量和会议只作背景。真正的周报主线是问题、假设、方法、证据和边界发生了什么变化。
5. 对重点论文不做礼貌性平均分。使用共享八维量表，至少给出证据位置与置信度；材料不足就写待核验。
6. 不把用户卡点等同于研究缺口。卡点是个人学习信号；研究缺口还必须通过相关工作和现有证据确认。

### 各素材的读取模式

| 目录 | extract | 怎么读 |
|---|---|---|
| `08-daily` | 题目聚合 | 只看 `daily_topics`，不逐篇读日报 |
| `03-notes` | 正文 | 优先通读（你的判断） |
| `02-markdown` | 正文 | 定点查证，不通读 |
| `04-equation_problem` | `question_files_only` | 只读疑问文件 + 标题骨架 |
| `08-reading` | `qa_log` | 读问答记录判断卡点 |
| `06-translation` | `existence_only` | 只标注存在性 |

## 步骤3：撰写分析报告

写进 **`report_path`**（即 `<research_dir>/<note_pattern 生成的文件名>`，默认 `07-research/<周起始日>-第N周周报.md`）。

**不要覆盖已有报告**：`07-research/` 里可能已有同主题历史文档（例如 `2026-09-15-大模型训练主流框架调研_2021-2026.md` 与 `2026-09-16-...`）。
- 新的时间窗就新建文件（`note_pattern` 按周起始日命名，天然不冲突）
- 若确实是对上一份的增量修订，在文末"同主题历史"列出旧文件并说明本次改了什么
- **绝不静默覆盖**

### 报告结构（问题地图 → 证据综合 → 个体卡点 → 研究决策）

```markdown
---
period: 2026-09-11 ~ 2026-09-17
week: 第1周
papers_reviewed: 6
domains: [随机梯度与优化理论, 大模型训练优化]
git_commits: 8
tags: [weekly-review, research-status]
---

# 第1周（2026-09-11 ~ 2026-09-17）研究现状与优化方向

## 本周执行摘要

用 5-8 句话回答：本周新增了什么证据；哪一项判断最可能改变当前研究；
有哪些结论仍不可靠；建议下周继续、停止或转向什么。另列新增论文、精读和推导数量。

## 一、本周证据边界

说明本周实际读取了哪些全文/精读、哪些只有摘要、哪些有代码或证明附录。列出因此无法判断的事项，避免把材料覆盖率误写成领域全景。

## 二、研究问题地图

### 主题分布
按 `daily_topics.domain_counts` 给出候选分布，只称“本周检索分布”。只有存在可比历史窗口时，才报告主题数量变化，并说明检索词或数据源变化是否会造成假趋势。

### 问题-方法-证据图
每个主题按“核心问题 → 现有假设 → 方法家族 → 本周新增证据 → 尚未解决”组织，引用具体论文；不要按论文逐篇摘要。

### 关键论文定位

| 论文 | 类型 | 最强主张 | 相对最强近邻的净增量 | 证据强度 | 关键边界 | 置信度 |
|---|---|---|---|---|---|---|
| ... | 理论/实证/系统/... | ... | ... | ... | ... | 高/中/低 |

### 共识与分歧
区分“结论一致”“证据互补”“实验设置不可比”和“真正矛盾”。对矛盾给出最可能的调节变量与最小判别实验。

## 三、主张-证据综合

| 研究命题 | 支持论文与证据 | 反对/限制证据 | 当前判断 | 还缺什么证据 |
|---|---|---|---|---|
| ... | 定理/表/图 | ... | 已支持/暂定/不支持 | ... |

重点论文按 `../research-evaluation-rubric.md` 给出八维评价。完整评分只用于读过正文的论文；摘要候选只给“待全文核验”的阅读优先级。

## 四、针对性分析：个人理解与能力瓶颈

材料来自 04 的 `疑问` 文件与 `08-reading` 的问答记录。逐条给出“卡点 → 症结 → 怎么补”，但不得把个人卡点冒充领域开放问题。

### 卡点清单

| # | 卡在哪 | 出处 | 症结类型 | 建议怎么补 |
|---|---|---|---|---|
| 1 | 为什么 clipped 后仍无偏 | 04/…/你的疑问.md | 证明细节 | 重看论文式 (3.4) 的期望展开 |
| 2 | 动量修正为何用二阶矩 | 08-reading/…_精读笔记.md | 概念理解 | 先推 MARS 的引理 1 再回看 |

症结类型建议用这几类：**概念理解 / 证明细节 / 符号记号 / 前置知识缺失 / 实现细节**。

### 逐个击破
对每个卡点给出针对性说明：
- 它本质上是什么问题（一句话点破）
- 需要补哪个前置知识或哪条引理（给出具体位置，如"论文式 (3.7) 与引理 2"）
- 一个自查方式（能自己验证懂了没有的最小练习）

### 掌握程度判断
基于问答记录判断哪些内容你已经过关、哪些还停在"能跟着看懂但推不出来"。
**只依据清单里的证据说，不要凭空推测**；证据不足就写"素材不足，无法判断"。

## 五、对当前课题的影响

### 1. 问题定义与理论层面
当前问题是否需要重述；哪些假设过强或不可验证；收敛率、下界或适用区域还有什么有证据支持的空间。

### 2. 方法与结构层面
算法设计、模块组织、训练与推理策略的可改进点。

### 3. 实验与评估层面
数据与污染风险、最强公平基线、统计不确定性、消融可识别性、失败案例和可复现性。

### 4. 工程与落地层面
（尤其关注你侧重的 **7B 级中小模型训练**）显存与吞吐、优化器实现代价、超参迁移、训练稳定性。

## 六、研究机会组合

| # | 可证伪假设 | 新颖性基线 | 最小验证 | 成功指标 | 停止条件 | 成本 | 依据 |
|---|---|---|---|---|---|---|---|
| 1 | … | 最接近工作与未覆盖点 | … | … | … | 低/中/高 | 论文/定理/表格 |

按优先级给 1-5 条，不为凑数硬写 3 条。至少覆盖一个低成本稳健方向和一个高风险高信息增益方向；每条必须能追溯到论文证据，不能只来自个人“不懂”。

## 七、下周研究计划

**这是你要带走的行动清单**，区分两类：

### 补基础（针对卡点）
- [ ] 具体动作 + 指向哪个文件/哪条定理（例如"补 PL 条件 → 读 04/…/全局推理.md 第 3 节"）

### 推进研究（针对方向）
- [ ] 最小实验：写清变量、对照、指标、预算和停止条件
- [ ] 精读候选：标明要核验的具体主张或定理，而不是只写“值得读”
- [ ] 决策点：实验出现什么结果时继续、转向或放弃

## 八、阅读与项目组合决策

| 对象 | 决策 | 具体用途 | 预计成本 | 下一检查点 |
|---|---|---|---|---|
| 论文/实验方向 | 必读/精读/选读/跟踪/停止 | ... | ... | ... |

## 同主题历史
- [上一份同主题报告](相对路径) —— 本次相对它改了什么（没有则写 `--`）
```

### 报告质量要求

- **必须可追溯**：每个结论都点名来源论文或卡点文件，不写"有研究表明"这类无主语结论。
- **区分三件事**：作者的主张 / 论文给出的证据 / 你自己的推断。推断要明确标成推断。
- **评分必须有证据**：分数后写章节、定理、表格或图；没有正文证据时不做全文评分。
- **比较必须找强近邻**：创新判断至少对照最接近的 2 篇工作，而不是只对照论文自己挑选的弱基线。
- **趋势需要基线**：没有历史可比窗口时，只报告本周分布，不写“升温”“下降”“成为趋势”。
- **建议要可执行**：写清"改什么、为什么这样改更好、怎么验证"，而不是"可以进一步研究"。
- **针对性一节不许空转**：如果本周没有任何 04 疑问或 08-reading 问答记录，就写
  "本周没有互动式精读记录"，**不要编造卡点**。
- **多维度不能硬凑**：某一维度本周确实没有素材就写 `--`。
- **同一篇论文只算一次**：`02-markdown/<YYYY-MM>/<标题>.md` 与 `03-notes/<YYYY-MM>/<标题>/精读.md` 属于同一篇（清单已按主干归并，可用 `month` 字段定位月份）。

## 步骤4：推进周期

报告写完后，写回日期，这样下一个 7 天窗口才会从今天算起：

```bash
python scripts/collect.py --mark-run
```

脚本会先校验 YAML 合法、再备份 `config.yaml`、然后写入 `start_date`（首次）与 `last_run`。

**只有报告确实落盘后才调用 `--mark-run`**，否则这一周的素材会被跳过。

## 步骤5：回报用户

- 报告路径（并给出 2-3 条最值得看的结论）
- 本次覆盖：时间窗口、论文数、来源
- 下次分析日期（清单里的 `next_due`）

# 注意

- **未到期就不要分析**。用户没要求时，`due: false` 的正确响应是告知下次日期。
- **不覆盖已有报告**。同一天重复运行时换一个主题名或加序号，不要静默覆盖。
- **不改用户笔记**。`02-markdown` / `03-notes` 一律只读。
- **不编造论文**。只分析清单里真实存在的文件；素材不足时如实说明。

# 依赖项

- Python 3.8+、`PyYAML`
- 与 `paper-daily` 同父目录（脚本从 `../paper-daily/scripts` 复用配置解析）
- 无需任何大模型 API key（分析由当前 agent 完成）
